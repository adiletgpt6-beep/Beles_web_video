# Приём исходника один раз

Источник истины — актуальная основная ветка GitHub. Проверяйте её и head перед публикацией; `ccr-443bddaf-7eho4h` — основная ветка на 2026-10-29. BW-001 — утверждённый эталон V5. Новый ролик регистрируется только при наличии нового файла. Готовый результат или новый референс сами по себе не являются новой съёмкой.

## Пользователь

Один раз отправьте видео ChatGPT и кратко укажите тему/пожелания; сайт нужен только для ролика о конкретном сайте. После проверенной публикации агент даст BW-ID и короткий промпт Claude Code. Повторно прикреплять это видео Claude не нужно. При смене чата достаточно ссылки на репозиторий и ID.

## 1. ChatGPT: регистрация

Прочитайте START_HERE, STATE, STYLE_GUIDE и очередь. Получите присланный оригинал из доступного вложения/Library, не перекодируйте. Если SHA-256 уже зарегистрирован, используйте существующее задание; BW-001 не открывайте повторно.

```bash
python3 scripts/beles.py queue
python3 scripts/beles.py ingest /absolute/path/new-video.mp4 --brief "Тема и пожелания пользователя" --language ky
```

ID выбирается автоматически, ожидаемый следующий — BW-002. Дополнительные параметры: `--title`, `--site`. Создаются `manifest.json`, `brief.md`, `checkpoint.json`, `HANDOFF.md` в отдельном каталоге; оригинал разделяется без перекодирования на бинарные части по 6 MiB в `production/media/<SHA-256>/`. Начальный статус `staged`: это ещё не подтверждённая доставка и не готовый вход Claude.

Защита: до 100 MiB на один исходник в этом реализованном транспорте; больший файл отклоняется до регистрации. Поддержка Release/объектного хранилища для больших файлов ещё не реализована и не проверена. Платный LFS, API и runners автоматически не включать. Ошибка `ffprobe` или изменение байтов при регистрации также прерывают приём.

## 2. ChatGPT: публикация и независимая проверка

Опубликуйте части, каталог задания, `production/registry.json` и `production/STATE.json` одним согласованным коммитом. Не включайте `input/`, lock-файлы или временные файлы. `ingest` готовит содержимое; публикацию выполняет агент через подключённый GitHub или уже авторизованный Git. Нельзя сообщать «загружено», опираясь только на локальные файлы.

Через GitHub connector: для каждой новой бинарной части — `create_blob(encoding=base64)`; проверьте возвращённый SHA против `git_blob_sha` из манифеста. Прикрепите все blob к `create_tree` (mode `100644`, type `blob`, path + sha); текстовые файлы можно передать в tree как UTF-8 content. Возьмите настоящее `commit.tree.sha` текущего head как base tree, создайте коммит с этим head в parent и обновите основную ветку с `force=false, expected_sha=<head>`. При отказе lease перечитайте ветку и согласуйте изменения. Не печатайте base64 видео в чат. Один unattached blob не является доставленным исходником.

Создайте новый каталог через **clone опубликованной ветки из GitHub**, без копирования старого MP4 или `input/`. В нём выполните:

```bash
python3 scripts/beles.py restore BW-XXX
python3 scripts/beles.py verify BW-XXX --record-delivery
```

Замените BW-XXX реально выданным ID. Проверяются размер, SHA-256 и Git SHA каждой части, суммарный MP4, длительность и потоки `ffprobe`. Установка MP4 атомарная, после всех проверок. `verify` без флага ничего не записывает. Флаг `--record-delivery` дополнительно требует, чтобы manifest и части совпадали с Git-объектами HEAD; сохраняет `delivery.json` с реальным commit и переводит новое задание `staged → queued`. Этот флаг запускать именно в независимом clone GitHub: сам факт наличия локального коммита ещё не доказывает загрузку на GitHub.

Опубликуйте `delivery.json`, обновлённые checkpoint/HANDOFF, registry и STATE. Проверьте удалённый head/файлы. Только после этого выдайте промпт Claude с существующим ID. `delivery_verification` в новых манифестах указывает путь доказательства; до появления `delivery.json` доставка не подтверждена.

## 3. Claude Code: продолжение

```bash
python3 scripts/beles.py status BW-XXX
python3 scripts/beles.py restore BW-XXX
python3 scripts/beles.py verify BW-XXX
python3 scripts/beles.py checkpoint BW-XXX --status in_progress --next-step "Расшифровать исходник и отметить лучшие дубли" --note "Прочитаны brief и STYLE_GUIDE"
```

Творческую адаптацию выполняет Claude в существующем Remotion/FFmpeg-стеке. Команда очереди не генерирует монтаж автоматически. Материалы нового задания — в `production/jobs/BW-XXX/` (например transcript, edit/timeline, subtitles, код и отчёт). Для них используйте отдельные пути и выходные имена. Утверждённые `src/`, `data/`, `release/` эталона не перезаписывайте под новый исходник.

После этапа сохраняйте точный следующий шаг и реальные артефакты:

```bash
python3 scripts/beles.py checkpoint BW-XXX --status in_progress --next-step "Проверить ө, ү, ң в 00:18–00:24; затем составить EDL" --note "Расшифровка сохранена; этот фрагмент ещё не проверен" --artifact production/jobs/BW-XXX/transcript.md
```

`--artifact` принимает существующий файл только внутри этого задания; флаг можно повторить. Повторный идентичный checkpoint не добавляет событие. Статусы: `staged`, `queued`, `in_progress`, `blocked`, `rendered`, `approved`. `rendered` означает полученный экспорт, не утверждение пользователя. `approved` разрешён только по явному утверждению пользователя с `--user-approved`; после этого задание закрыто для изменения командой checkpoint. BW-001 всегда закрыт.

При блокере сохраните `--status blocked` с причиной и точным действием для снятия блокера. `next` выбирает сначала `in_progress`, затем `queued`; `staged` и `blocked` автоматически не запускаются. Платных API, Actions, рендера или отправки сообщений команды не вызывают.

Перед сменой чата/длительным этапом опубликуйте checkpoint, HANDOFF задания, registry, STATE и все нужные рабочие файлы в GitHub; при существенных изменениях обновите общий HANDOFF. Локальный checkpoint без коммита не сохраняет прогресс между средами.

## Восстановление и ремонт индекса

```bash
python3 scripts/beles.py queue
python3 scripts/beles.py next
python3 scripts/beles.py status BW-XXX
python3 scripts/beles.py restore BW-XXX
python3 scripts/beles.py verify BW-XXX
python3 scripts/beles.py sync
```

`restore` повторяем: правильный MP4 остаётся; удалённый/повреждённый собирается заново. Если часть удалена/повреждена в рабочем каталоге, команда берёт объявленный blob из локальной Git object database и проверяет его перед установкой. Если объект недоступен, получите опубликованный commit из GitHub или сделайте новый clone; команда завершится ошибкой, сохранив прежний MP4.

Manifest + checkpoint каждого задания — первичные данные. Registry и HANDOFF — производные; после прерывания их можно восстановить через `sync`. Удалённый checkpoint задания с монтажом автоматически не выдумывается: восстановите опубликованный файл Git. Lock защищает одновременные изменения в одном checkout; конфликт между разными чатами предотвращается проверкой head/lease при публикации.

Новые исходники, собственно монтаж, прослушивание и финальная оценка имеют отдельные проверки. Не выдавайте проверку архива за просмотр или прослушивание готового ролика. Подписка ChatGPT/Claude не оплачивает сторонние API.
